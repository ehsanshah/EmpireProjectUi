# Phase 13 administration contract decision — Demo boundary

Status: proposed UI seam; **not** reconciled with Live Engine. Date: 2026-10-28.

The reference API catalog proposes `GET/POST P/memberships`, `PATCH P/memberships/{id}`, `GET O/principals`, `GET O/groups`, `GET/POST P/role-bindings`, `GET P/schemas`, `GET/POST P/workflows`, workflow validations/publications, and `GET/POST P/connections` with checks. The catalog explicitly says paths and methods need actual OpenAPI operation IDs. No current OpenAPI, session/CSRF sample, grant lineage schema, workflow migration response, connection probe result, or staging URL was available. `LiveCoreClient` has no Phase 13 methods; it is not given Demo fallbacks.

`DemoCoreClient.phase13` is a deterministic, project-scoped local adapter. It derives effective actions from explicit grants and active membership, not role names. Its role bindings are display metadata with independent revisions. Human, Agent and Group memberships, project vs organization flags, access previews, version checks, idempotency keys, Demo receipts and permission revision invalidations are local simulations. Revoking an Agent principal invalidates the existing Phase 10 Demo readiness record. Core page cursors, selection tokens and previews are cleared; a scoped `PermissionChanged` event is emitted, then the Demo stream is closed. This does not prove server authorization or replay behavior.

The settings draft owns a versioned local snapshot. Validation checks schema integrity, transition endpoints and required fields, board mappings/WIP, calendar/timezone, template safety, missing status migration mappings and active Run implications. Approval binds to the draft hash/revision and policy revision; publication is a separate idempotent command with a Demo receipt. Migration touches only mapped Demo issues through the adapter and preserves unrelated fields. Existing active Runs block affected status migration. The UI retains edits on errors. Published Demo issue types, priorities and custom fields feed the shared WorkItem schema; WIP limit and timezone update the existing Board/Calendar state. The local Demo now publishes editable Board column names/order/status mappings and Area swimlane order to the actual renderer. It validates unique known status mappings, fixed column IDs, lane capabilities and WIP scope, previews affected issues/unmapped statuses, and persists only the published settings per project. Unmapped issues remain in the tray; configuration does not change business statuses. WIP and Board moves use full project scope and versioned rank anchors. The renderer supports Area (Web/Mobile) ordering; Assignee grouping remains unavailable. Live publication/migration still require the reconciled Engine configuration contract. Existing Board/WorkItem surfaces retain their approved behavior.

Connection configuration accepts only an opaque `credref:` reference and endpoint label. It never echoes credentials, calls an external API/MCP endpoint, or marks health, authorization, probe or readiness as passed. SSO/SCIM, retention, residency, quotas, billing and real probe controls are explicitly unavailable. Product/IAM/Backend/DevOps must supply capability and policy contracts before Live controls can appear enabled.

Required reconciliation inputs: generated OpenAPI with operation IDs and ETags; membership/grant/role and group lineage examples; permission-change event/stream reset and ACL cache policy; workflow version/migration/active Run/approval schemas and receipts; connection credential-reference and probe transport; organization capability payload; authorized staging with admin/restricted identities. Exit evidence is real staging tests for denial, stale grants, migration, revocation, stream purge and credential handling.
