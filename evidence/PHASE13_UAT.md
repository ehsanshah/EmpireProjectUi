## UX review checklist — interaction and truth

- [ ] **Admin access journey:** Open People as Sara. Preview revoke for Ali; read project scope, current allowed actions and affected Runs before Apply. Apply once and see a Demo receipt and policy revision change. Switch to Ali lens; restricted content is hidden. Switch back to Sara, preview restore; Ali's organization membership remains separate and old grants do not return.
- [ ] **Role binding:** On People, scroll to Role bindings. Preview changing Ali's label to “Project owner.” The preview lists the same allowed actions. Apply and confirm that the label changes but no `people.write` or `workflow.publish` grant appears. An explicit grant uses its own preview, policy revision and receipt.
- [ ] **Workflow:** Open Settings → Create draft. Change a required transition field to an undefined key, Save draft, Validate; approval stays disabled with a reason. Correct the field and save a new revision. Validate again; inspect affected issue and active Run panels. Approve current hash, then separately Publish; only a publish receipt changes the published version. Use Back to return to prior work view.
- [ ] **Board configuration journey:** In a fresh session, open Board and note the default Backlog → To Do order and Web → Mobile lanes. Open Settings → Create draft. Rename To Do to “Ready next”; move it earlier; map Review to Unmapped tray; move Mobile earlier. Save draft and Validate. Review the column/lane changes, affected issue keys and unmapped status count. Approve current revision, then Publish with receipt. Use the **Team board** navigation in the same session; verify the new order/name/lane layout and the review issues in the tray. Reload; the published layout remains. Existing issue statuses stay unchanged.
- [ ] **Approval and conflict:** After approving a draft, edit any Board name. Publish becomes disabled for unsaved changes. Save and verify that approval disappears; validate and approve the new revision. A stale draft revision is rejected without deleting local edits. Select Ali in the Demo policy lens; that restricted member cannot approve or publish.
- [ ] **WIP and keyboard:** With a mapping that places Review in the In Progress WIP column, set a low limit in the versioned draft and publish. A move into the full column is rejected with the card still at its source. Test a card menu move, pointer drag and Alt + arrow on the configured Board; all use the validated command path, and a successful move shows a Demo receipt. The WIP count covers all project issues, including hidden filters and the other lane.
- [ ] **Migration:** In a fresh Demo session, remove a used status from the draft. Save/Validate; missing mapping is called out. Choose a target mapping and save again. If an affected issue has an active Phase 10 Run, publish is blocked; there is no silent Run/approved-plan migration. Existing issue custom values remain intact.
- [ ] **Connection:** Enter an opaque `credref:` reference for API/MCP and save. Configuration may become true while health remains unknown, probe stays `not_run` and readiness is not inferred. Enter a raw secret-like value; the form reports rejection. No external provider is called.
- [ ] **Permissions/conflict/recovery:** Switch to restricted Ali while active; edit and publish controls are denied by the adapter. A stale access preview or draft revision must return a conflict without erasing local edits. Revoking Hermes membership makes Phase 10 Demo readiness false. Archive/restore never revives old grants. Permission changes clear scoped Demo cursors/previews and close the affected Demo stream.
- [ ] **Keyboard/history:** Tab through navigation, access actions, form controls and admin tabs; press Enter to activate a focused tab. Use browser Back and in-app Back. Check the project scope when switching between Empire and Payment; no membership change should apply to the wrong project.
